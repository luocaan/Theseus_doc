模组开发指南

面向第三方开发者的完整开发流程：环境搭建 → 最小模组 → 核心示例 → 打包发布

本指南面向希望为 SEECMD 开发第三方模组的开发者，覆盖从环境搭建到打包发布的完整流程。v2 指南以「能力原语 + 内容注册表 + 渲染上下文抽象（RenderCanvas）」为核心：模组不是等宿主提供功能钩子，而是自由组合「读数据 / 改状态 / 画东西」的原语，并注册新内容。

API 状态：本文档中所有接口标注 @Experimental（实现中，可能调整）。各部分功能状态见相应章节说明。完整接口签名见 mod-api.md，分层结构与核心抽象见 mod-system-design.md。

1. 环境搭建

JDK

  • JDK 17 或更高版本。模组代码使用 Java 17 语言特性（record、sealed、switch 模式匹配等均可）。
  • 推荐使用与宿主一致的 JDK 发行版编译，避免字节码版本不匹配。

依赖引用

模组开发需要将 SEECMD 的 mod-api 瘦身 jar 作为编译期依赖。该 jar 仅含 com.seecmd.mod.api.*（含子包）与 com.seecmd.mod.api.spi.*，剥离了宿主实现与游戏内核，是第三方模组唯一应依赖的宿主产物。

获取方式：mod-api jar 随游戏发布，也可从 Theseus 文档站 直接下载。下载后安装到本地 Maven 仓库：

bash
mvn install:install-file -Dfile=mod-api-0.6.7.jar -DgroupId=com.seecmd -DartifactId=mod-api -Dversion=0.6.7 -Dpackaging=jar

安装成功后即可按以下坐标引用。

Maven 示例：

xml
<dependencies>
    <dependency>
        <groupId>com.seecmd</groupId>
        <artifactId>mod-api</artifactId>
        <version>0.6.7</version>
        <scope>provided</scope>
    </dependency>
    <!-- api.spi 的签名参数（JsonObject）依赖 Gson，宿主运行期提供 -->
    <dependency>
        <groupId>com.google.code.gson</groupId>
        <artifactId>gson</artifactId>
        <version>2.10.1</version>
        <scope>provided</scope>
    </dependency>
</dependencies>

scope 必须为 provided / compileOnly：API 由宿主在运行期提供，模组 jar 不得把宿主类打进去，否则会引发类加载冲突。

Gradle 示例：

groovy
dependencies {
    compileOnly 'com.seecmd:mod-api:0.6.7'
    compileOnly 'com.google.code.gson:gson:2.10.1'
}

包依赖说明

模组编译期仅依赖 com.seecmd:mod-api 瘦身 jar，该 jar 仅含 com.seecmd.mod.api.* 与 com.seecmd.mod.api.spi.*，从物理上隔离了 API 与宿主/内核。标准库类（java.* / java.util.* / java.nio.file.* 等）按需 import，java.awt.Color 作为纯值对象允许使用；绘制统一走抽象 RenderCanvas，不接触任何平台图形 API。

2. 最小模组

最小模组只需实现 Mod 接口，提供 info() 元信息，并按需覆写 onLoad(ModContext)。

java
package com.example.helloworld;

import com.seecmd.mod.api.Mod;
import com.seecmd.mod.api.ModContext;
import com.seecmd.mod.api.ModInfo;

import java.util.List;

public class HelloWorldMod implements Mod {

    @Override
    public ModInfo info() {
        return ModInfo.of(
                "com_example_helloworld",   // id：小写下划线
                "Hello World",               // 显示名
                "0.1.0",                     // 版本
                List.of("Alice"),            // 作者
                "最小模组示例"               // 描述
        );
    }

    @Override
    public void onLoad(ModContext ctx) {
        // onLoad 在模组被启用时调用一次，此处可读取配置、初始化资源、注册内容
        ctx.getLogger().info("Hello World 模组已加载");
        // 数据目录在首次访问时自动创建
        ctx.getLogger().info("数据目录: " + ctx.getDataDir());
    }
}

关键点

  • Mod.info() 是唯一必须实现的方法；onLoad / onUnload 有默认空实现，按需覆写。
  • ModInfo.of(...) 构造无依赖的模组信息；若需声明依赖，使用 ModInfo record 全参构造或 dependsOn 字段（见 第 12 节）。
  • 若模组需要参与游玩（滤镜/判定/事件），改实现 GameplayMod 接口（继承自 Mod），见后续章节。
  • ModContext 是模组的「工具箱」：读取日志 / 数据目录 / 配置，并在 onLoad 中注册内容（noteTypes() / gameModes() / judgmentKinds() / chartExtensions()）与能力（capabilities()）。

3. 核心示例一：替换进度条

已实现：本示例使用的能力接口（GameplayHud / RenderCanvas）已落地并可编译运行。

设计思路（能力原语，而非功能封装）：宿主不提供「把进度条替换成指定样式」这类方法，只提供三件原语——

  1. 改状态：setProgressVisible(false) —— 隐藏原版进度条（覆盖机制）；
  2. 读数据：values().progress() —— 读取进度数值；
  3. 画东西：renderOverlay(canvas, hudCtx) —— 由模组自绘。

样式完全由模组决定，宿主不预设任何「皮肤」概念。

java
package com.example.neonprogress;

import com.seecmd.mod.api.GameplayMod;
import com.seecmd.mod.api.ModContext;
import com.seecmd.mod.api.ModInfo;
import com.seecmd.mod.api.capability.GameplayHud;
import com.seecmd.mod.api.context.HudContext;
import com.seecmd.mod.api.context.HudValues;
import com.seecmd.mod.api.render.RenderCanvas;

import java.awt.Color;
import java.util.List;

/** 把原版进度条替换成自绘的霓虹风格。 */
public class NeonProgressMod implements GameplayMod, GameplayHud {

    private HudValues hud;              // 宿主注入的 HUD 数值快照
    private boolean progressHidden = true;

    @Override
    public ModInfo info() {
        return ModInfo.of("com_example_neon_progress", "Neon Progress", "0.1.0",
                List.of("Alice"), "把进度条替换成霓虹风格");
    }

    @Override
    public void onLoad(ModContext ctx) {
        // 注册本模组为 GameplayHud 能力：宿主在每个游玩场景自动注入并回调
        ctx.capabilities().register(GameplayHud.class, this);
        // 改状态：隐藏原版进度条（覆盖机制的开关）
        setProgressVisible(false);
    }

    // ===== GameplayHud 实现 =====

    /** 读数据：宿主提供 HUD 数值（progress / combo / score / accuracy ...）。 */
    @Override
    public HudValues values() {
        return hud;
    }

    /** 改状态：进度条可见性开关。 */
    @Override
    public void setProgressVisible(boolean visible) {
        this.progressHidden = !visible;
    }

    @Override
    public void setComboVisible(boolean visible) { /* 本例不覆盖连击 */ }

    @Override
    public void setScoreVisible(boolean visible) { /* 本例不覆盖分数 */ }

    @Override
    public void setAccuracyVisible(boolean visible) { /* 本例不覆盖准度 */ }

    /** 画东西：宿主在覆盖渲染阶段调用，本模组自绘霓虹进度条。 */
    @Override
    public void renderOverlay(RenderCanvas canvas, HudContext hudCtx) {
        if (!progressHidden) {
            return; // 防御：仅在本模组隐藏了原版时才自绘
        }
        double p = values().progress();            // 读原版进度数值
        int x = 40, y = 700, w = 600, h = 8;        // 示意坐标，可按需调整
        canvas.setColor(Color.BLACK);
        canvas.fillRect(x, y, w, h);                // 底槽
        canvas.setColor(new Color(0, 255, 200));
        canvas.fillRect(x, y, (int) (w * p), h);    // 已播放部分
        canvas.setAlpha(0.5);
        canvas.drawRect(x, y, w, h);                // 半透明描边
        canvas.setAlpha(1.0);
    }
}
实时预览实时预览：上面这段 renderOverlay 代码在游戏里绘制出的霓虹进度条

要点

  • 覆盖语义：宿主先查开关——setProgressVisible(false) 后原版进度条不再绘制；随后在覆盖渲染阶段调用 renderOverlay。
  • 只有「有组件被隐藏」时宿主才调用 renderOverlay，零模组覆盖时无额外开销（见第 8 节）。
  • RenderCanvas 是模组唯一允许的绘制入口，杜绝接触平台图形 API（Graphics2D / GraphicsContext）。
  • HudValues 已注入：values() 返回本帧实时 progress/combo/score/accuracy 等数值快照。

4. 核心示例二：MISS 一次打开自己的 galgame

接入状态：本示例使用的能力接口（SceneHost / Scene / GameStateAccess / AudioAccess）均已接入主循环，游玩场景中 capabilities().get(Xxx.class) 返回可用实例。本示例已可实际运行。

设计思路（跨域能力组合）：模组可影响游戏每一处——把「判定事件（NoteJudgedEvent）+ 状态机（GameStateAccess）+ 场景栈（SceneHost）+ 音频（AudioAccess）+ 自定义场景（Scene）」自由组合，就能实现「MISS 一次打开自带的 galgame」。宿主不需要为此提供任何专用钩子。

text
NoteJudgedEvent (judgment == seecmd:miss)
  → game.pause()                            // 改状态：暂停游玩（可被 resume 恢复）
  → audio.playSound(...)                    // 改状态：播放自配音效
  → scenes.push(new MyGalgameScene(...))    // 改状态：压入自定义场景
  → (galgame 场景内由模组自绘、自处理输入)
  → 玩家返回时：scenes.pop() + game.resume() // 恢复游玩
java
package com.example.missgalgame;

import com.seecmd.mod.api.GameplayMod;
import com.seecmd.mod.api.ModContext;
import com.seecmd.mod.api.ModInfo;
import com.seecmd.mod.api.capability.AudioAccess;
import com.seecmd.mod.api.capability.GameStateAccess;
import com.seecmd.mod.api.capability.SceneHost;
import com.seecmd.mod.api.event.ModEventBus;
import com.seecmd.mod.api.event.NoteJudgedEvent;
import com.seecmd.mod.api.event.Subscription;
import com.seecmd.mod.api.render.RenderCanvas;
import com.seecmd.mod.api.scene.InputEvent;
import com.seecmd.mod.api.scene.Scene;

import java.awt.event.KeyEvent;
import java.util.ArrayList;
import java.util.List;

/** MISS 一次就打开模组自带的 galgame。 */
public class MissGalgameMod implements GameplayMod {

    private final List<Subscription> subs = new ArrayList<>();
    private GameStateAccess game;
    private SceneHost scenes;
    private AudioAccess audio;

    @Override
    public ModInfo info() {
        return ModInfo.of("com_example_miss_galgame", "Miss Galgame", "0.1.0",
                List.of("Alice"), "MISS 时打开自带的 galgame");
    }

    @Override
    public void onLoad(ModContext ctx) {
        // 取用宿主注入的能力实例
        game = ctx.capabilities().get(GameStateAccess.class);
        scenes = ctx.capabilities().get(SceneHost.class);
        audio = ctx.capabilities().get(AudioAccess.class);
    }

    @Override
    public void registerEvents(ModEventBus bus) {
        subs.add(bus.subscribe(NoteJudgedEvent.class, e -> {
            // 判定等级为 JudgmentKindDefinition，用 id() 判断
            String kind = e.result().judgment().id();
            if ("seecmd:miss".equals(kind)) {
                openGalgame();
            }
        }));
    }

    private void openGalgame() {
        game.pause(); // 1. 暂停游玩（音乐走 pause/resume，保持进度）
        audio.playSound("com_example_miss_galgame:alert", 0.8); // 2. 自配音效
        scenes.push(new MyGalgameScene(game, scenes)); // 3. 压入自定义场景
    }

    @Override
    public void onUnload() {
        for (Subscription s : subs) {
            s.unsubscribe();
        }
        subs.clear();
    }
}

/** 模组自定义场景，实现 API 场景抽象 `Scene`（接口已定义，宿主未接线，见节首提示）。 */
class MyGalgameScene implements Scene {

    private final GameStateAccess game;
    private final SceneHost scenes;

    MyGalgameScene(GameStateAccess game, SceneHost scenes) {
        this.game = game;
        this.scenes = scenes;
    }

    @Override
    public String id() {
        return "com_example_miss_galgame:galgame";
    }

    @Override
    public void render(RenderCanvas canvas) {
        // 模组自绘 galgame 画面：立绘、对话框、选项按钮……
    }

    @Override
    public boolean handleInput(InputEvent event) {
        if (event.keyCode() == KeyEvent.VK_ESCAPE) {
            scenes.pop();   // 退出 galgame 场景
            game.resume();  // 恢复游玩（AudioEngine 恢复播放位置）
            return true;    // 已消费
        }
        return false;
    }
}

要点

  • 暂停语义：pause() 暂停的是游玩与音乐，resume() 恢复并维持原播放位置与速度（符合宿主 MusicPlayer 的 pause/resume 约定）。不要用 endGame() 结束本局。
  • 场景语义：SceneHost.push(scene) 压入新场景后当前游玩场景挂起；pop() 弹回。Scene 是 API 场景抽象（com.seecmd.mod.api.scene），host 内部桥接到内核 SceneManager，模组不必接触内核场景类。
  • 返回后游玩从暂停点继续，无需模组做任何状态复原。

5. 核心示例三：注册新音符类型

注册表框架已实现：NoteTypeDefinition / NoteTypeRegistry / JudgeInput / JudgeSink 等类型均已落地，可注册、查询、遍历。 核心循环尚未切换：谱面解析 / 判定引擎 / 轨道渲染当前仍按内置音符类型派发，尚未切换到定义对象派发。本示例说明 API 用法；要让自定义音符类型真正参与游玩派发，需等待后续版本。

设计思路（内容注册表）：现状音符类型是写死的枚举（NORMAL/HOLD/BARRIER/EXPLOIT/PAYLOAD），模组无法「加内容」。v2 中，音符类型开放为注册表——模组实现 NoteTypeDefinition（解析 + 判定 + 渲染三件套），注册后宿主通用路径自动消费，谱面里写上对应类型 key 即生效。

java
package com.example.slidenote;

import com.google.gson.JsonObject;

import com.seecmd.mod.api.GameplayMod;
import com.seecmd.mod.api.ModContext;
import com.seecmd.mod.api.ModInfo;
import com.seecmd.mod.api.render.RenderCanvas;
import com.seecmd.mod.api.spi.JudgeInput;
import com.seecmd.mod.api.spi.JudgeSink;
import com.seecmd.mod.api.spi.JudgmentKindRegistry;
import com.seecmd.mod.api.spi.NoteData;            // api 侧音符基类
import com.seecmd.mod.api.spi.NoteParseContext;
import com.seecmd.mod.api.spi.NoteRenderContext;
import com.seecmd.mod.api.spi.NoteTypeDefinition;
import com.seecmd.mod.api.spi.NoteTypeRegistry;

import java.awt.Color;
import java.util.List;

/** 注册新音符类型「滑键 slide」。 */
public class SlideNoteMod implements GameplayMod {

    @Override
    public ModInfo info() {
        return ModInfo.of("com_example_slide_note", "Slide Note", "0.1.0",
                List.of("Alice"), "新增滑键音符类型");
    }

    @Override
    public void onLoad(ModContext ctx) {
        // 注册到音符类型注册表（进程级，仅一次）
        ctx.noteTypes().register(new SlideNoteDefinition(ctx.judgmentKinds()));
    }
}

/** 滑键定义：解析、判定、渲染全部由本类负责。 */
class SlideNoteDefinition implements NoteTypeDefinition {

    private final JudgmentKindRegistry kinds; // 用于产出判定等级

    SlideNoteDefinition(JudgmentKindRegistry kinds) {
        this.kinds = kinds;
    }

    @Override
    public String id() {
        return "com_example_slide_note:slide";
    }

    @Override
    public String displayName() {
        return "滑键";
    }

    /** 谱面 JSON 中该音符的序列化 key（type 字段）。 */
    @Override
    public String serializationKey() {
        return "slide";
    }

    /** 解析：从谱面 JSON 对象创建运行时音符。 */
    @Override
    public NoteData deserialize(JsonObject json, NoteParseContext ctx) {
        SlideNote note = new SlideNote();
        note.setTime(json.get("time").getAsLong());
        note.setLane(json.get("lane").getAsInt());
        if (json.has("endLane")) {
            note.setEndLane(json.get("endLane").getAsInt());
        }
        return note;
    }

    /** 判定：音符到达判定线时，按时间差产出判定等级。 */
    @Override
    public void onJudge(JudgeInput input, JudgeSink sink) {
        long delta = Math.abs(input.deltaMs());
        if (delta <= 70) {
            sink.accept(kinds.get("seecmd:perfect"), input.judgeTime());
        } else if (delta <= 150) {
            sink.accept(kinds.get("seecmd:great"), input.judgeTime());
        } else {
            sink.accept(kinds.get("seecmd:miss"), input.judgeTime());
        }
    }

    /** 渲染：每帧在音符位置绘制滑键外观。 */
    @Override
    public void render(RenderCanvas canvas, NoteRenderContext ctx) {
        canvas.setColor(new Color(0, 180, 255));
        canvas.fillRect(ctx.x(), ctx.y(), ctx.width(), 8);
        canvas.setColor(new Color(0, 120, 255));
        canvas.drawLine(ctx.x(), ctx.y() + 4, ctx.x() + ctx.width(), ctx.y() + 4);
    }
}

/** 滑键运行时数据，继承 api 侧音符基类。 */
class SlideNote extends NoteData {
    private int endLane;

    void setEndLane(int endLane) {
        this.endLane = endLane;
    }

    int endLane() {
        return endLane;
    }
}

谱面 JSON 怎么写

serializationKey() 与谱面 JSON 中音符的 type 字段对应。宿主解析谱面时用 NoteTypeRegistry.bySerializationKey("slide") 找到本定义，再调用 deserialize 创建运行时音符：

json
{
  "title": "Slide Demo",
  "author": "Bob",
  "difficulty": "Hard",
  "bpm": 140,
  "lanes": 4,
  "notes": [
    {
      "type": "slide",
      "time": 5000,
      "lane": 1,
      "endLane": 3
    },
    {
      "type": "slide",
      "time": 5200,
      "lane": 2,
      "endLane": 0
    }
  ]
}

要点

  • 通用路径消费：宿主核心循环（谱面解析 / 判定引擎 / 轨道渲染）不再为每种类型写 if/else，而是遍历注册表分发。新增类型自动获得「能解析、能判定、能渲染」的完整能力。
  • 判定等级来自注册表：onJudge 通过 sink.accept(kinds.get("seecmd:perfect"), time) 产出判定，评分 / 统计 / 特效按 JudgmentKindRegistry 遍历，无需硬编码枚举。
  • 其余三种注册表（游戏模式 GameModeRegistry、判定等级 JudgmentKindRegistry、谱面扩展段 ChartExtensionRegistry）的注册方式与本节同构：onLoad 中 ctx.xxx().register(...) 一次。

6. 判定修改

判定修改分两类，语义不同，不可混用（ 可用）：

类型接口作用合并语义
policy（策略）JudgmentPolicy定义判定时间窗口多个 policy 取最大值（最宽松）
adjuster（调整器）JudgmentAdjuster改写判定结果多个 adjuster 链式级联

核心区分：policy 是宽松判定（放大窗口，让玩家更容易命中），多模组叠加取最大值；adjuster 是收紧/改写判定（如把 PERFECT 降级为 GREAT），按注册顺序依次改写结果。若想"收紧判定"，必须用 adjuster，因为 policy 只会越合越宽。

实时预览实时预览：判定窗口可视化（默认 vs 宽松 ×1.5，可拖拽指针）
实时预览实时预览：连击行为 INCREMENT / RESET / NONE（点击徽章可编辑）

JudgmentPolicy 注册示例（WideJudgeMod 风格）

将全部 5 个判定窗口放大 1.5 倍。五个字段语义统一为"值越大越宽松"。

java
import com.seecmd.mod.api.GameplayMod;
import com.seecmd.mod.api.ModInfo;
import com.seecmd.mod.api.judge.JudgmentPolicy;
import com.seecmd.mod.api.judge.JudgmentPolicyRegistry;

import java.util.List;

public class WideJudgeMod implements GameplayMod {

    // 基础窗口 70/150/150/150/50 × 1.5
    private static final long PERFECT_WINDOW_MS = 105L;
    private static final long GREAT_WINDOW_MS   = 225L;
    private static final long MISS_WINDOW_MS    = 225L;
    private static final long HOLD_END_WINDOW_MS = 225L;
    private static final long LATE_CUTOFF_MS    = 75L;

    @Override
    public ModInfo info() {
        return ModInfo.of("com_example_wide_judge", "Wide Judge", "0.1.0",
                List.of("Alice"), "宽松判定（×1.5）");
    }

    @Override
    public void registerJudgmentPolicy(JudgmentPolicyRegistry registry) {
        registry.registerPolicy(new JudgmentPolicy() {
            @Override public long perfectWindowMs()  { return PERFECT_WINDOW_MS; }
            @Override public long greatWindowMs()    { return GREAT_WINDOW_MS; }
            @Override public long missWindowMs()     { return MISS_WINDOW_MS; }
            @Override public long holdEndWindowMs()  { return HOLD_END_WINDOW_MS; }
            @Override public long lateCutoffMs()     { return LATE_CUTOFF_MS; }
        });
    }
}

窗口字段含义：

  • perfectWindowMs / greatWindowMs / missWindowMs：各判定等级的时间容忍时长。
  • holdEndWindowMs：长音符结尾判定窗口。
  • lateCutoffMs：越过判定线后仍可补判的时长。

无任何 policy 注册时，宿主使用内置默认策略 70/150/150/150/50（见 mod-api.md 附录 A）。

JudgmentAdjuster 注册示例（PERFECT → GREAT 收紧）

java
import com.seecmd.mod.api.GameplayMod;
import com.seecmd.mod.api.ModContext;
import com.seecmd.mod.api.ModInfo;
import com.seecmd.mod.api.context.GameplayContext;
import com.seecmd.mod.api.judge.JudgeResult;
import com.seecmd.mod.api.judge.JudgeResults;
import com.seecmd.mod.api.judge.JudgmentAdjuster;
import com.seecmd.mod.api.judge.JudgmentPolicyRegistry;
import com.seecmd.mod.api.spi.JudgmentKindRegistry;

import java.util.List;

public class StrictJudgeMod implements GameplayMod {

    private JudgmentKindRegistry kinds; // onLoad 时取得，用于查询内置/自定义判定等级

    @Override
    public ModInfo info() {
        return ModInfo.of("com_example_strict_judge", "Strict Judge", "0.1.0",
                List.of("Alice"), "将 PERFECT 收紧为 GREAT");
    }

    @Override
    public void onLoad(ModContext ctx) {
        this.kinds = ctx.judgmentKinds();
    }

    @Override
    public void registerJudgmentAdjuster(JudgmentPolicyRegistry registry) {
        registry.registerAdjuster(new JudgmentAdjuster() {
            @Override
            public JudgeResult adjust(JudgeResult input, GameplayContext ctx) {
                // 判定等级为 JudgmentKindDefinition，用 id() 判断
                String id = input.judgment() != null ? input.judgment().id() : "";
                // 仅当 combo 较高时收紧，避免新手期过严
                if (ctx.combo() >= 50 && "seecmd:perfect".equals(id)) {
                    return JudgeResults.withJudgment(input, kinds.get("seecmd:great"));
                }
                return input; // 不改写时原样返回
            }
        });
    }
}

JudgeResults 工具类

JudgeResult 为只读接口，改写时必须通过 JudgeResults 静态工厂构造新实例（不可变）：

方法说明
JudgeResults.withJudgment(src, judgment)仅替换判定等级，保留 note/judgeTime/isHoldEnd
JudgeResults.withJudgeTime(src, judgeTime)仅替换判定时间
JudgeResults.with(src, judgment, judgeTime)同时替换判定等级与时间
java
// 例：把 PERFECT 降级为 GREAT，并把判定时间对齐到音符时间
JudgeResult rewritten = JudgeResults.with(
        input,
        kinds.get("seecmd:great"),   // JudgmentKindDefinition
        input.note().time()
);

withJudgment / with 的第二个参数为 JudgmentKindDefinition（从 JudgmentKindRegistry 取得，内置等级 id：seecmd:perfect / seecmd:great / seecmd:miss / seecmd:none）。

调整器行为约定

  • 返回 null 会被跳过并记 WARNING：当前结果保持不变，链继续往后执行。若不想改写，请显式 return input;，不要返回 null。
  • adjuster 不可修改 note 字段：JudgeResults 不提供 withNote(...)，判定结果的音符引用始终与输入一致。这是有意限制——判定改写不应改变被判定音符本身。
  • 异常隔离：adjuster 抛异常会被跳过（当前结果不变）并经 LogLimiter 限频记录，不影响后续 adjuster 与游戏运行。
  • NONE → MISS 转换：调整链结束后，若最终判定等级 id 仍为 seecmd:none，宿主自动改写为 seecmd:miss。

多 adjuster 链式级联

调整器按注册顺序链式执行，前一个的输出作为后一个的输入：

text
policy 判定 → adjuster#1.adjust(result) → adjuster#2.adjust(...) → ... → 计分/特效

因此 adjuster 链对顺序敏感。跨模组的注册顺序遵循 ModManager.register 调用顺序（见 第 7 节）。模组作者应假设链中可能存在其他 adjuster，避免依赖"输入必然是某等级"的假设。

判定等级：自定义判定（已实现并接入）

判定等级已统一为注册表驱动：初始判定产物为内置等级（seecmd:perfect / seecmd:great / seecmd:miss / seecmd:none），JudgeResult.judgment() 直接返回 JudgmentKindDefinition；JudgmentKindRegistry + JudgmentKindDefinition 已实现并接入主循环——GameplayScene.applyJudgment 以 JudgmentKindDefinition 驱动计分 / 连击 / 血量 / 渲染，ScoreManager.addJudgment(def) 统一处理内置与自定义判定等级。

调整器改写到自定义判定等级的方式：

java
registry.registerAdjuster((input, gameplayCtx) -> {
    String id = input.judgment() != null ? input.judgment().id() : "";
    if ("seecmd:perfect".equals(id)) {
        return JudgeResults.withJudgment(input, this.kinds.get("mymod:good"));
    }
    return input;
});

要点：

  • 自定义判定的 comboBehavior 决定连击行为：INCREMENT 递增、RESET 归零（按 miss 语义处理，清空连击显示）、NONE 不变。
  • scoreValue() / accuracyWeight() 参与计分与血量；color() 与 render() 决定判定特效与连击文字的样式。
  • 注意 RESET 类判定在当前设计中不显示连击行（与 miss 同语义），但会写入日志与统计（见第 7 节日志）。

7. 事件监听

模组通过 ModEventBus 订阅游玩事件。在 GameplayMod.registerEvents 中注册订阅（ 可用）。

实时预览实时预览：一场游玩中模组订阅到的事件序列与数据

7 个游玩事件触发时机

事件触发时机
ChartLoadedEvent谱面加载完成（loading step4 完成、谱面数据已加载、音乐未启动）。此时 musicTimeMs 为负（入场过渡期），progress 为 0。适合读取谱面元数据做预处理。
GameplayStartEvent游玩正式开始（loading 完成后）。
NoteJudgedEvent单个音符判定完成后（applyJudgment 之后）。含判定结果与游玩状态快照。
ComboBreakEventcombo 从 >0 变为 0 时触发一次，紧随对应的 NoteJudgedEvent 之后。连续 MISS 不会重复触发（combo 已是 0）；重启谱面时 combo 归零不触发。
PauseEvent游玩被暂停时。
ResumeEvent游玩从暂停恢复时。
GameplayEndEvent游玩结束、进入结算（goToResult）前。

所有事件均提供 context() 返回不可变的 GameplayContext 快照；NoteJudgedEvent 额外提供 result() 返回 JudgeResult。

订阅与取消订阅

subscribe 返回 Subscription 令牌，模组应在 onUnload 时取消所有订阅，避免内存泄漏。

java
import com.seecmd.mod.api.GameplayMod;
import com.seecmd.mod.api.ModContext;
import com.seecmd.mod.api.ModInfo;
import com.seecmd.mod.api.event.ChartLoadedEvent;
import com.seecmd.mod.api.event.ComboBreakEvent;
import com.seecmd.mod.api.event.ModEventBus;
import com.seecmd.mod.api.event.NoteJudgedEvent;
import com.seecmd.mod.api.event.Subscription;

import java.util.ArrayList;
import java.util.List;

public class StatsMod implements GameplayMod {

    private final List<Subscription> subscriptions = new ArrayList<>();
    private ModContext ctx;

    @Override
    public ModInfo info() {
        return ModInfo.of("com_example_stats", "Stats", "0.1.0",
                List.of("Alice"), "统计与事件示例");
    }

    @Override
    public void onLoad(ModContext ctx) {
        this.ctx = ctx;
    }

    @Override
    public void registerEvents(ModEventBus bus) {
        subscriptions.add(bus.subscribe(ChartLoadedEvent.class, e -> {
            ctx.getLogger().info("谱面加载: " + e.context().chartTitle()
                    + " / 总音符 " + e.context().totalNoteCount());
        }));

        subscriptions.add(bus.subscribe(NoteJudgedEvent.class, e -> {
            // 统计 PERFECT 数等
        }));

        subscriptions.add(bus.subscribe(ComboBreakEvent.class, e -> {
            ctx.getLogger().info("Combo 中断！最高连击 " + e.context().maxCombo());
            // 可在此触发屏幕震动、闪屏等特效
        }));
    }

    @Override
    public void onUnload() {
        for (Subscription s : subscriptions) {
            s.unsubscribe();
        }
        subscriptions.clear();
    }
}

ModEventBus 内部对 handler 持有弱引用兜底：模组未取消订阅且实例被 GC 时会自动清理，但不保证时效，仍应显式 unsubscribe。事件 publish 同步执行，不支持异步。

游玩事件仅场景内可见

GameplayModHost（含游玩 ModEventBus）在每次进入 GameplayScene 时重新构造，离开场景时销毁。因此：

  • 游玩事件仅在 GameplayScene 内发布与可见，菜单、选歌、结算等场景不会收到游玩事件。
  • 模组的 registerEvents 在每次进入游玩时被重新调用，订阅是"本次游玩内有效"的。不要把跨场景的全局状态挂在事件闭包里而不清理。

跨模组订阅顺序

事件分发给同一事件类型的多个订阅者时，顺序遵循 ModManager.register 的调用顺序（注册表保持插入顺序）。因此：

  • 多个模组订阅同一事件时，先注册的模组先收到。
  • 这与判定 adjuster 链的顺序规则一致。

NoteJudgedEvent → ComboBreakEvent 同 tick 顺序保证

当一次 MISS 导致 combo 归零时，宿主保证同一判定 tick 内先发布 NoteJudgedEvent，紧接着发布 ComboBreakEvent。模组可安全地假设：在收到 ComboBreakEvent 时，对应的 NoteJudgedEvent 已被所有订阅者处理完毕。

全局事件（已实现）

本小节使用全局事件总线（GlobalEventBus），已实现并接入主循环：MainApp 发布启动 / 关闭事件，SceneManager 发布场景切换事件，SettingsScene 发布设置变更事件。

游玩事件是场景级的；跨场景的横切关注点（启动 / 关闭 / 场景切换 / 设置变更）用全局事件，通过 ModContext.globalEventBus() 订阅，进程级有效：

java
@Override
public void onLoad(ModContext ctx) {
    ctx.globalEventBus().subscribe(SceneChangedEvent.class, e -> {
        // 场景切换后触发：e.from() / e.to() 返回 SceneInfo
        ctx.getLogger().info("场景切换: " + e.from().id() + " -> " + e.to().id());
    });

    ctx.globalEventBus().subscribe(SettingsChangedEvent.class, e -> {
        // 设置变更后触发：e.changedKeys() 返回变更键集合
        ctx.getLogger().info("设置变更: " + e.changedKeys());
    });
}

全局事件目录（继承 GlobalEvent 标记接口）：

事件类触发时机方法
GameStartupEvent游戏启动完成（模组加载后）无额外数据
GameShutdownEvent游戏关闭前无额外数据
SceneChangedEvent场景切换后from() → SceneInfo；to() → SceneInfo
SettingsChangedEvent游戏设置变更后changedKeys() → Set<String>

两条总线的生命周期差异：

维度全局总线（ModContext.globalEventBus()）游玩总线（GameplayMod.registerEvents 传入）
作用域进程级，整个游戏生命周期有效场景级，仅 GameplayScene 内有效
重建时机游戏启动时创建，关闭时销毁每次进入游玩时重建
适用场景菜单 / 选歌 / 结算等跨场景游玩内判定 / 暂停 / 结束

8. 渲染覆盖细节

「替换原版渲染」的场景统一使用覆盖机制，避免为每种组件发明新 API：

text
① 开关：setXxxVisible(false)           —— 宿主在默认渲染该组件时检查开关，被覆盖则不画原版
② 读数：values() / context()           —— 模组读取被覆盖组件的底层数据
③ 覆盖：renderOverlay(canvas, hudCtx)  —— 宿主在覆盖渲染阶段调用，模组在 canvas 上自绘

覆盖的触发与开销

  • 宿主先查覆盖、被覆盖则不画原版：GameplayHud.renderOverlay 只在有模组调用过 setXxxVisible(false) 时才被调用；没有任何组件被隐藏时，宿主不调用覆盖渲染，无额外开销（与「无滤镜零开销」原则一致）。
  • 同一 HUD 组件被多个模组覆盖时按注册顺序叠加，后注册的覆盖先绘制（位于上层）。

z 顺序约定（自底向上）

text
NOTES（轨道/音符） → JUDGE_FX（判定特效） → HUD（原版 HUD）
→ OVERLAY（renderOverlay 覆盖层） → FULLSCREEN（全屏覆盖层）

模组在 HudContext.layer() 中可查询当前绘制阶段，在 HudContext.zOrder() 中查询覆盖层 z 顺序，避免覆盖层与特效层误叠：

java
@Override
public void renderOverlay(RenderCanvas canvas, HudContext hudCtx) {
    // 仅在全屏覆盖层之上绘制自定义演出元素
    if (hudCtx.layer() != RenderLayer.FULLSCREEN) {
        return;
    }
    // ...
}

覆盖的通用写法

java
// onLoad 中请求隐藏 + 注册能力
ctx.capabilities().register(GameplayHud.class, this);
setProgressVisible(false);

// renderOverlay 中读数据 + 自绘
double p = values().progress();
canvas.setColor(Color.WHITE);

9. 打包规范

打包为 jar

模组编译后打包为标准 jar，必须包含 META-INF/MANIFEST.MF。manifest 声明模组入口类与元信息，供游戏加载器和外置模组管理工具读取。

Manifest 字段表

字段必填说明
Seecmd-Mod-Class是模组入口类全限定名，游戏加载器据此实例化模组
Seecmd-Mod-Id否（建议）模组 id，用于日志。实际 id 从 Mod.info() 读取，不一致时以 Mod.info() 为准
Seecmd-Mod-Name否（建议）模组显示名称，外置管理工具列表展示
Seecmd-Mod-Version否（建议）模组版本号，外置管理工具列表展示
Seecmd-Mod-Authors否（建议）作者列表，逗号分隔（如 Alice, Bob）
Seecmd-Mod-Description否（建议）简介文本，外置管理工具详情面板展示
Seecmd-Mod-Icon否图标资源路径（jar 内，如 icon.png），外置管理工具展示
Seecmd-Mod-Notes否备注文本，作者写给用户的使用说明/注意事项，外置管理工具详情面板展示
Seecmd-Mod-Depends-On否依赖模组 id 列表，逗号分隔，外置管理工具据此检查依赖完整性

重要：除 Seecmd-Mod-Class 外，其余字段虽非必填，但强烈建议填写。外置模组管理工具（mods/mod-manager.jar）从 manifest 读取这些字段展示模组信息，不实例化模组类。未填写的模组在管理工具中将显示为空或默认值。

一致性约定：Mod.info() 返回的 id/name/version/authors/description/dependsOn 应与 manifest 声明保持一致。运行时游戏以 Mod.info() 为准，外置工具以 manifest 为准。

图标资源

  • 格式：PNG（支持透明通道）
  • 推荐尺寸：64×64 像素（外置管理工具按此尺寸展示）
  • 路径声明：通过 manifest 的 Seecmd-Mod-Icon 指定 jar 内资源路径（如 icon.png、assets/icon.png）
  • 资源放置：图标文件作为 jar resources 打包，与 class 文件同级或放在 resources/ 子目录
  • 缺失处理：未声明或文件不存在时，外置管理工具显示默认占位符

备注字段

Seecmd-Mod-Notes 是作者写给用户的说明文本，区别于 Seecmd-Mod-Description（简短一句话简介）：

  • Description：一句话简介，用于列表快速识别（建议 ≤ 50 字）
  • Notes：详细说明，可包含使用注意事项、已知问题、配置说明等（建议多行，无长度限制）

通过 jar 加载

宿主已提供 jar 加载器，扫描模组 jar 的 manifest 定位入口类，加载并注册到 ModManager。

加载路径：游戏工作目录下的 mods/ 文件夹（与 data/ 同级）。不存在则跳过加载（不自动创建）。

加载时机：游戏启动时，在内置模组注册之后、enabledMods 激活之前。仅启动时扫描一次，不支持运行时热加载。

manifest 要求：

  • 必须含 Seecmd-Mod-Class（入口类全限定名）
  • Seecmd-Mod-Id/Seecmd-Mod-Version 可选，仅用于日志；实际 id 从 Mod.info() 读取，与 manifest 不一致时以 Mod.info() 为准

ClassLoader 隔离：每个 jar 使用独立 URLClassLoader，parent ClassLoader 加载 com.seecmd.mod.api.* 包，保证模组间共享 API 类型。模组类之间默认隔离。

异常隔离：单个 jar 加载失败（文件损坏/manifest 缺失/类找不到/不是 Mod 子类型/实例化失败/id 冲突）返回 false 并限频记录日志，不影响其他 jar 与游戏运行。

非模组 jar 跳过：mods/ 目录下可能存在非模组 jar（如外置模组管理工具 mod-manager.jar）。这类 jar 的 manifest 缺少 Seecmd-Mod-Class，加载器静默跳过（INFO 日志，不报错）。

外置模组管理工具

游戏随分发包提供外置模组管理工具 mods/mod-manager.jar，玩家可双击或通过 java -jar mods/mod-manager.jar 启动。

功能：

  • 扫描 mods/ 目录，列出所有模组（名称、版本、启用状态）
  • 选中模组查看详情：图标、名称、版本、作者、简介、备注、依赖、加载状态
  • 勾选/取消勾选启用状态，点击"保存设置"持久化到 data/settings.json 的 enabledMods
  • 依赖缺失的模组标红显示，详情面板提示缺失的依赖 id
  • 损坏 jar 标红显示"读取失败"

工作原理：

  • 工具从 jar 的 META-INF/MANIFEST.MF 读取模组元信息，不实例化模组类，不依赖游戏 jar
  • 工具自身 manifest 含 Main-Class 但不含 Seecmd-Mod-Class，因此游戏加载器会跳过它
  • 工具推断游戏根目录为自身所在 mods/ 的父目录，据此访问 data/settings.json

模组 id 命名规范

  • 小写下划线，如 com_example_wide_judge。
  • 不得以 builtin_ 开头：该前缀保留给游戏内置模组（如 builtin_glitch、builtin_monochrome、builtin_wide_judge）。
  • 建议使用反向域名前缀避免冲突：<域名反转>_<功能名>，例如 com_example_stats、org_myteam_hardcore。
  • id 在整个游戏内必须唯一，重复注册会被忽略并告警。

10. 数据目录约定

ModContext.getDataDir() 返回模组专属数据目录：

text
data/mods/{modId}/

例如 com_example_stats 模组的数据目录为 data/mods/com_example_stats/。

约定

  • 目录在首次访问 getDataDir() 时自动创建（含父目录）。创建失败不抛异常，模组在后续读写时自行处理 IO 异常。
  • 模组只允许在此目录内读写自有数据文件，不应访问其他游戏目录。
  • 模组配置文件 config.json 由 ModContext.config() 自动管理于本目录（见 第 11 节），无需手动拼路径。
java
@Override
public void onLoad(ModContext ctx) {
    Path dataDir = ctx.getDataDir(); // data/mods/com_example_stats/
    Path scoresFile = dataDir.resolve("scores.json");
    // 在此目录内读写自定义数据文件
}

11. 配置文件

ModContext.config() 返回 ModConfig，封装 data/mods/{modId}/config.json 的读写。

特性

  • 扁平 key-value JSON：值类型限定 String / Integer / Double / Boolean / List<Object>。复杂结构请模组自行 JSON 序列化为 String 存储单个 key。
  • 懒加载：首次调用 get 时加载；文件不存在返回默认值且不创建空文件。
  • 同步写盘：set 调用时立即持久化到磁盘。
  • 线程安全：实例方法 synchronized 保护，可在事件处理器与滤镜中并发访问。
  • 解析失败：文件存在但 JSON 非法时记 WARNING 并返回默认值（不抛异常）。

API

方法说明
get(key, default)读取字符串，不存在返回默认值
getInt(key, default)读取整数，不存在或类型不符返回默认值
getBool(key, default)读取布尔，不存在或类型不符返回默认值
getDouble(key, default)读取浮点，不存在或类型不符返回默认值
set(key, value)写入并同步持久化
getAll()返回全部配置的只读 Map 视图

示例

java
public class ConfigDemoMod implements GameplayMod {
    private ModContext ctx;

    @Override
    public void onLoad(ModContext ctx) {
        this.ctx = ctx;
        ModConfig cfg = ctx.config();

        // 读取配置（带默认值）
        boolean debug = cfg.getBool("debug", false);
        int maxParticles = cfg.getInt("maxParticles", 200);
        double intensity = cfg.getDouble("intensity", 0.8);

        if (debug) {
            ctx.getLogger().info("maxParticles=" + maxParticles + ", intensity=" + intensity);
        }

        // 首次运行写入默认值
        if (!cfg.getAll().containsKey("installed")) {
            cfg.set("installed", true);
            cfg.set("version", 1);
        }
    }
}

对应 config.json：

json
{
  "debug": true,
  "maxParticles": 300,
  "intensity": 0.9,
  "installed": true,
  "version": 1
}

12. 依赖声明

ModInfo.dependsOn 字段声明模组间的硬依赖（被依赖的模组 id 列表）。

拓扑排序激活

  • 宿主按 dependsOn 关系对启用模组做拓扑排序，依赖在前、被依赖在后，依次调用 onLoad。
  • 被依赖模组必须已注册且处于启用/已激活状态，否则依赖它的模组激活失败。

缺失依赖

  • 若 dependsOn 中的某个 id 既未注册也未激活，宿主抛出 MissingDependencyException，该模组状态标记为 LOAD_FAILED。
  • 可通过 ModManager.getLoadError(modId) 获取异常，MissingDependencyException.getMissing() 返回缺失的 id 列表。

循环依赖

  • 若依赖关系成环（如 A→B→A），环上所有模组标记为 LOAD_FAILED。
  • MissingDependencyException.getCircularChain() 返回环上的 id 列表，首尾相同（如 ["A","B","A"]）。
  • 错误信息中会列出完整环路径。

当前版本限制

  • 当前版本仅支持硬依赖（dependsOn）。可选依赖、版本范围匹配等能力后续版本提供。

示例

java
@Override
public ModInfo info() {
    // 使用 record 全参构造声明依赖
    return new ModInfo(
            "com_example_stats_ext",       // id
            "Stats Extension",             // name
            "0.1.0",                       // version
            List.of("Alice"),              // authors
            "依赖基础统计模组的扩展",       // description
            List.of("com_example_stats")   // dependsOn：硬依赖 com_example_stats
    );
}

模组 id 和 dependsOn 中的 id 必须严格匹配（小写下划线，区分大小写）。建议依赖关系双方约定稳定的 id，避免重命名导致断链。

13. 日志调试

获取 Logger

ModContext.getLogger() 返回 java.util.logging.Logger，名称为 seecmd.mod.{modId}：

java
@Override
public void onLoad(ModContext ctx) {
    Logger log = ctx.getLogger(); // Logger 名: "seecmd.mod.com_example_stats"
    log.info("模组已加载");
    log.fine("详细调试信息"); // FINE 级别，默认不输出
}

与 LogLimiter 集成

模组系统的异常隔离日志（滤镜/调整器/事件异常、加载失败等）通过项目内置的 LogLimiter 限频输出，5 秒窗口内同一 key 只打印一次，窗口内累计抑制次数会在下次打印时附注 suppressed N times。这避免高频路径（如每帧滤镜、每次判定）的日志洪水。

模组自身通过 getLogger() 输出的日志走标准 JUL 通道；当模组在回调中抛异常时，宿主会经 LogLimiter 限频记录（而非崩溃）。

日志级别建议

级别用途
SEVERE模组无法继续工作的致命错误（极少使用）
WARNING可恢复的异常、降级行为、不合规输入
INFO生命周期事件（加载/卸载）、关键状态切换
FINE详细调试信息，默认不输出，按需开启

通过 config.json 控制 FINE 输出

推荐做法：在模组配置中提供 debug 开关，仅在开启时输出 FINE 日志，避免生产环境噪声。下面用事件回调演示（不依赖渲染 API，任何回调位置同理）：

java
private Logger log;
private boolean debug;

@Override
public void onLoad(ModContext ctx) {
    this.log = ctx.getLogger();
    this.debug = ctx.config().getBool("debug", false);
    if (debug) {
        log.setLevel(java.util.logging.Level.ALL);
        log.fine("FINE 日志已开启");
    }
}

@Override
public void registerEvents(ModEventBus bus) {
    bus.subscribe(NoteJudgedEvent.class, e -> {
        if (debug) {
            log.fine("judged t=" + e.context().musicTimeMs()
                    + " misses=" + e.context().misses());
        }
    });
}

注意：每帧输出 FINE 日志即便被 JUL 抑制也会有字符串拼接开销，建议用 log.isLoggable(Level.FINE) 守卫，或仅在 debug 为真时拼接。

14. 异常反馈

仅日志记录，不弹窗

  • 所有模组异常仅记录日志（经 LogLimiter 限频），不弹窗。当前版本没有面向玩家的模组错误 UI。
  • 单个模组的异常不会崩溃游戏：宿主对每个外部回调均做 try-catch 隔离。

当前版本行为

场景行为
onLoad 失败模组状态标记为 LOAD_FAILED，异常可通过 ModManager.getLoadError(id) 读取；模组不进入 active 列表
滤镜 apply 异常跳过该滤镜本次调用，记 WARNING，其他滤镜与渲染不受影响
调整器 adjust 异常跳过该调整器，当前结果不变，记 WARNING，链继续
调整器返回 null跳过该调整器（当前结果不变）并记 WARNING
事件订阅者异常跳过该订阅者，记 WARNING，其他订阅者仍收到事件
注册钩子异常该钩子注册内容作废，模组仍进入 host 参与其他钩子
注册表回调异常（音符/模式/判定/扩展）跳过本次回调，记 WARNING；对应内容可能缺渲染或行为，无崩溃
能力接口方法调用异常本次调用失效，记 WARNING；对应能力本次不生效，无崩溃
onUnload 异常记录日志，模组仍从 active 移除，不阻塞其他模组卸载

LOAD_FAILED 状态

ModManager.getLoadStatus(id) 返回 ModLoadStatus 枚举：

  • NOT_REGISTERED：未注册
  • REGISTERED：已注册未启用
  • LOAD_FAILED：启用但 onLoad 失败（含依赖缺失/循环依赖/抛异常）
  • ACTIVE：已激活
  • UNLOADED：当前版本不出现，保留供后续版本

后续计划

后续版本将提供管理 UI，集中展示各模组的状态与加载错误（基于 getLoadStatus / getLoadError），玩家可在界面内查看失败原因。当前版本开发者通过日志排查。

15. 谱面字段

谱面 metadata 可声明两项模组相关字段，供玩家在选歌详情面板检查：

字段类型含义
requiredLaneWidthdouble谱面建议的轨道宽度。0 表示不指定；玩家打开详情面板时，若该值与当前游戏设置不等，会弹窗提示。
requiredModsList<String>谱面建议启用的模组 id 列表。玩家打开详情面板时，若未启用列表中的模组，会弹窗提示。

谱面 JSON 示例

json
{
  "title": "Demo Chart",
  "author": "Bob",
  "difficulty": "Hard",
  "metadata": {
    "requiredLaneWidth": 12.0,
    "requiredMods": ["com_example_wide_judge", "com_example_stats"]
  }
}

说明

  • 这两个字段是建议性的：仅弹窗提示玩家，不强制启用或拦截游玩。玩家可选择忽略提示继续游玩。
  • requiredMods 中的 id 必须与模组 ModInfo.id() 严格匹配。
  • 谱面作者在分发谱面时，应同步说明所依赖模组的获取方式，避免玩家找不到对应模组。

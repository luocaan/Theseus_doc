架构设计

模组系统的分层结构与核心抽象（面向开发者的公开版）

本文介绍 SEECMD 模组系统的分层结构与关键抽象，帮助开发者理解「模组能做什么、为什么这样设计」。 接口签名的唯一权威定义见 API 参考；完整开发流程见 开发指南。

包边界强制规则

包面向依赖职责
com.seecmd.mod.api（含 context / render / capability / judge / event 子包）第三方模组开发者仅标准库 + java.awt.Color（纯值对象），不依赖游戏内核消费侧纯接口与不可变 record：模组可触达的全部读口、开关、绘制入口
com.seecmd.mod.api.spi第三方模组开发者仅 api 包 + 标准库供给侧注册骨架：定义接口 + 注册表入口，模组实现并注册新内容
com.seecmd.mod.host宿主自身api + spi + 游戏内核实现管理器、场景托管、注册表、RenderCanvas 实现、上下文快照
com.seecmd.mod.builtin宿主自带示例仅 api + spi（与第三方模组同等约束）内置示例模组，验证 API 与作为开发参考

强制规则：

  • 模组代码只允许 import com.seecmd.mod.api.* 与 com.seecmd.mod.api.spi.*（含子包）。
  • 禁止 import 宿主实现包（com.seecmd.mod.host.*）或游戏内核包（com.seecmd.core.* / com.seecmd.gameplay.* / com.seecmd.model.* 等），也不得通过反射访问非 API 类。
  • 标准库（java.* / javax.* / java.util.* / java.nio.file.* 等）按需 import；java.awt.Color 作为纯值对象允许使用；禁止依赖 java.awt.Graphics2D / java.awt.image.BufferedImage 等图形实现类。
  • mod-api 瘦身 jar（仅含 api 与 api.spi）已从物理上隔离 API 与宿主/内核。违反包边界的模组可能因内部重构而失效，宿主不保证兼容。

2. 内容注册表语义

四个注册表（音符类型 / 游戏模式 / 判定等级 / 谱面扩展段）共享同一套注册语义，此处统一定义。

2.1 通用语义

语义规格
id 唯一注册项 id() 全局唯一，使用命名空间格式 <modId>:<name>（如 seecmd:hold、mymod:slide）。重复注册被忽略并告警。
注册时机进程级，在 Mod.onLoad(ModContext) 中经 ModContext.noteTypes() / gameModes() / judgmentKinds() / chartExtensions() 注册一次；非场景级、非每局重注册。
生命周期每个注册项按「解析 → 行为 → 渲染」三阶段被宿主调用：谱面加载时解析（deserialize / parse）→ 游玩中派发行为（onJudge / onUpdate / onJudged）→ 每帧渲染（render）。
异常隔离注册项的每个回调方法单独 try-catch，抛异常则跳过本次调用并记 LogLimiter 限频日志，不影响其他注册项与游戏运行。
通用路径消费宿主的核心循环（谱面解析、判定引擎、轨道渲染）不再为每种类型写 if/else，而是遍历注册表分发。当前谱面解析、行为判断、判定（onJudge）与渲染（render）均已按定义对象委托——判定时宿主调用 onJudge 派发自定义判定等级，渲染时宿主对自定义类型调用 render 由其自绘，回调异常由宿主捕获并回退内置逻辑。外观方面，皮肤系统已支持为自定义类型提供专属槽位（图片 <类型key>.png / 字符 custom 映射，见资源制作指南），未提供时回退到行为分类对应槽位。

2.2 四个注册表

注册表注册内容解决的问题
NoteTypeRegistryNoteTypeDefinition音符「类型」本身开放为内容：新增一种音符，定义其解析、判定与渲染方式
GameModeRegistryGameModeDefinition游戏模式开放为内容：定义模式专属的行为与规则
JudgmentKindRegistryJudgmentKindDefinition判定等级开放为内容：新增 PERFECT/GREAT/MISS 之外的判定等级，评分、统计、特效按注册表遍历
ChartExtensionRegistryChartExtensionParser谱面 JSON 增加 extensions 扩展段解析机制，谱面可携带模组自定义数据

2.3 核心循环分发

核心循环只做一件事——把控制权交给内容定义对象：

java
noteType.onCreateRuntime(chartNote);   // 谱面解析 → 运行时音符
noteType.onJudge(input, sink);         // 判定 → 定义对象决定产出哪个判定等级
noteType.render(canvas, renderCtx);    // 渲染 → 定义对象决定怎么画

接入现状：解析、行为判断、判定（onJudge）与渲染（render）均已接入核心循环——自定义类型被判定时宿主调用 onJudge 派发判定等级，渲染时由定义对象自绘；内置类型不派发，回调异常由宿主捕获并回退内置逻辑。自定义类型的外观已可由皮肤系统按类型定制（见资源制作指南）。

3. 能力目录（capabilities）

能力接口是「模组影响游戏每一处」的载体。每个能力接口按「读数据 / 改状态 / 渲染覆盖」三件套组织。能力实例在 Mod.onLoad 中经 ModContext.capabilities() 注册，宿主在每个游玩场景自动注入可用。

能力接口域读数据改状态渲染覆盖
GameplayHud游玩 HUDvalues() → HudValues（progress/combo/score/accuracy/musicTimeMs）setProgressVisible(boolean) / setComboVisible / setScoreVisible / setAccuracyVisiblerenderOverlay(RenderCanvas, HudContext)
GameStateAccess游玩状态机musicTimeMs() / isPaused() / isFinished()play() / pause() / resume() / seek(ms) / setSpeed(x) / endGame()—
SceneHost场景栈current()push(Scene) / pop() / replace(Scene)—
AudioAccess音频—playSound(String soundId, double volume) / stopSound(String) / playMusic(String) / stopMusic() / setMusicVolume(double)—
InputAccess输入isKeyDown(int)subscribeKeyHandler(Consumer<InputEvent>) / consumeKey(int)—
StoryAccess剧情currentNode()trigger(String nodeId, StoryContext) / skip()—
ModManagerAccess模组管理（进程级）registeredMods() / enabledMods() / isEnabled(String) / isActive(String) / getLoadStatus(String) / getLoadError(String)setEnabled(String, boolean)（立即生效并持久化）—

能力接口只含原语方法。例如「把进度条换成自定义风格」＝ setProgressVisible(false) + 读 values().progress() + renderOverlay 自绘，宿主不提供「进度条皮肤」概念。

3.1 渲染覆盖模型

所有「替换原版渲染」的场景统一使用同一套覆盖机制，避免为每种组件发明新 API：

text
① 开关：setXxxVisible(false)           —— 宿主在默认渲染该组件时检查开关，被覆盖则不画原版
② 读数：values() / context()           —— 模组读取被覆盖组件的底层数据
③ 覆盖：renderOverlay(canvas, hudCtx)  —— 宿主在覆盖渲染阶段调用，模组在 canvas 上自绘

宿主先查覆盖、被覆盖则不画原版：GameplayHud.renderOverlay 只在有模组调用过 setXxxVisible(false) 时才被调用；同一 HUD 组件被多个模组覆盖时按注册顺序叠加，后注册的覆盖先绘制（位于上层）。

z 顺序约定（自底向上）：轨道/音符 → 判定特效 → 原版 HUD → renderOverlay 覆盖层 → 全屏覆盖层。模组在 HudContext.layer() 中可查询当前绘制阶段。

3.2 跨域组合示例

「miss 一次打开模组自带的 galgame」由能力接口自由组合即可实现，无需宿主提供任何专门钩子：

text
NoteJudgedEvent (judgment == MISS)
  → GameStateAccess.pause()          // 改状态：暂停游玩
  → SceneHost.push(myGalgameScene)   // 改状态：压入自定义场景
  → AudioAccess.playSound(...)       // 改状态：播放自配音效
  → (galgame 场景内由模组自行渲染，回到游玩后)
  → GameStateAccess.resume()         // 改状态：恢复游玩

4. 渲染上下文 RenderCanvas 规格

4.1 定位

RenderCanvas 是模组唯一允许的绘制入口。宿主内部以 JavaFX GraphicsContext 实现，模组只面对抽象，不感知底层平台。

4.2 能力边界

可画说明
填充矩形 fillRect(x, y, w, h)实心矩形，支持半透明（setAlpha）
边框矩形 drawRect(x, y, w, h)1px 描边矩形
直线 drawLine(x1, y1, x2, y2)1px 直线
文本 drawText(String, x, y, TextStyle) / measureText(...)复用游戏现有位图字形体系（CmdCharRenderer / FxProportionalTextRenderer）
图像 drawImage(RenderImage, x, y, w, h)经 RenderResources.loadImage(...) 获取的句柄
裁剪 clip(x, y, w, h)配合 save()/restore() 使用
变换 translate/scale/rotate状态栈管理，save 与 restore 必须成对
不可说明
接触 GraphicsContext / Graphics2D实现细节，模组永远拿不到
接触窗口 / Canvas 组件由 SceneHost 负责，渲染层不开放
像素级读写底层图像需要后处理时使用「覆盖渲染 + 半透明叠加」达成

4.3 颜色表示

颜色统一使用 java.awt.Color（纯值对象，非图形上下文）。宿主在 RenderCanvas 实现内部转换为平台颜色。允许使用 java.awt.Color 不构成「实现泄漏」——它只是值对象，不携带任何绘图能力。
